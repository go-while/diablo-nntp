#208 (parsedate formats): needs a short discussion before it lands. We found two
real correctness items in the parser and have fixes ready:
 1. impossible dates (e.g. 31 Feb, 29 Feb in a non-leap year) parse as valid
    instead of being rejected -- they should fail the calendar check.
 2. a zone written as GMT+H (single digit) or GMT+HH:MM (with a colon) is read
    wrong (single digit treated as UTC; colon minutes dropped), while GMT+HH and
    GMT+HHMM work. GMT-like zero-offset bases should take the numeric offset;
    a named zone like BST-1 keeps BST.
Bigger picture, and we'd like your view: for a live feeder, is the extended
format set (ctime / ISO / US-slash / ordinals / epoch) worth carrying, or is an
INN-style RFC-5322-lax parser enough? Modern clients emit valid RFC, so the
real-world discrepancy looks small, and an INN-style parser fixes both items
above by construction. We have INN checked out and can model it closely. If you
have a concrete diablo use for the archive formats (old-spool import etc.) we
keep the extended parser plus the two fixes; if not, #208 could shrink to an
INN-style RFC-lax parser. Either way the Date is only parsed when
feedermaxacceptage > 0 (bypassed at 0), and the default stays your stock
behaviour. go-while will follow up on the direction.
