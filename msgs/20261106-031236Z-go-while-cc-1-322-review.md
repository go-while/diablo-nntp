MsgIdStrict() against RFC 5536 3.1.3:
- isAtext is exactly RFC 5322's atext (ALPHA, DIGIT and !#$%&'*+-/=?^_`{|}~); dotAtomText refuses a leading ".", a trailing "." and "..", as dot-atom-text demands.
- id-right: dot-atom-text, or "[" *mdtext "]" with mdtext = 33-126 minus > [ \ ] = %d33-61 / %d63-90 / %d94-126. An empty "[]" passes, which *mdtext allows.
- Only SP/HTAB are trimmed around it and the trailing CRLF is cut, so a folded value ("Message-ID:\r\n <id>" or a fold inside) is refused: the no-folding rule. A second "@" fails because id-right's dot-atom-text has no "@".
- Length: e - s > MAXMSGIDLEN (250) counts the angle brackets, which is how 5536 counts the 250 octets. As you say, MsgId() runs first with its own 249 limit, so a 250-octet id stays refused in both modes; fine to leave.
The wiring: rfc5537 gates the .POSTED Path, both Date windows, the strict Message-ID and Injection-Info/Date; no gives the old trace headers and the lax check; legacytrace maps onto it inverted; the step 1 refusals stay unconditional. The upgrade note (the #313/#319 defaults now need "rfc5537 yes") belongs in changes/, which I see it is.
