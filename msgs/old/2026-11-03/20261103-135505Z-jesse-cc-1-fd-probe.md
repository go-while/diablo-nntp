[Claude] Probe results. Method: an AF_UNIX socketpair, sendmsg() of 64 bytes plus one SCM_RIGHTS fd, then fill the table with dup() until EMFILE (RLIMIT_NOFILE 64). Then recvmsg(MSG_DONTWAIT) once with the table full, and once more after the dups are closed. Run as a non-root user.

**Linux 6.12 (Debian 13), all three types:** recvmsg=64 with MSG_CTRUNC and no cmsg. The message is gone afterwards (EAGAIN). This is what #266 handles.

**FreeBSD 15.1:**
- SEQPACKET and STREAM: the first recvmsg is -1/EMFILE and the message stays queued. The second gets the 64 bytes with no cmsg and no MSG_CTRUNC (flags 0x80 is just MSG_DONTWAIT echoed). The fd itself is lost.
- DGRAM: -1/EMFILE, then EAGAIN; the whole message is gone.

**illumos (SmartOS):** all three types give -1/EMFILE, then EAGAIN. Data and fd are both gone.

What that means for main.c's reader-socket loop (`while (RecvMsg(...) == sizeof(dres))`), from reading the code, not run:
- **FreeBSD:** the -1 ends the loop with one "recvmsg error (Too many open files)" log. On the next select pass the data arrives with recv_fd -1, the `recv_fd < 0` branch runs, and NumActive/d_Count are released. So no leak there, only an extra log line.
- **illumos:** the DnsRes is lost, so that slot is never released (Act stays up). That is the old leak, still there on illumos. reader.c's RecvMsg loop (main to reader hand-off) presumably drops the client the same way there, though I have not checked it.
- **A possible fix:** RecvMsg treats -1/EMFILE (and ENFILE) as "descriptor lost". On FreeBSD that means reading the message again, which then arrives without its fd. On illumos the message itself is gone, so main.c can't know which client it was. That needs something else, e.g. headroom so the receiver never reaches the limit, or a periodic reconciliation of d_Count against the reader's own count.
