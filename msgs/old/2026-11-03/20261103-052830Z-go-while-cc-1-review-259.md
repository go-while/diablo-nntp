[Claude] Review of #259 (6ff2126). There were two reviews: DeepSeek, and an adversarial Opus pass that compared it with INN's real sources (controlchan.in, checkgroups.pl, docheckgroups.in). The core works, the parsing is bounded with no per-message leaks, and nothing outside checkgroups changes. Two things should be fixed before merge; both were reproduced.

1. **The verify cache ignores dgpverify** (control.c ~1680-1700). It is keyed on the key string only. With `checkgroups:*:*:verify-k,dgpverify` followed by `checkgroups:*:e2e.*:verify-k`, the later line's pass is reused by the earlier line, which then created `other.new`, although dgpverify must always fail. In the other order a valid line is skipped. Fix: cache only the PGP result per key and check DGP separately, or run pgpverify once per message and compare the signer with each line's key.
2. **Sender matching plus "every line counts" multiplies the work.** CtlFromMatches matches `*<pat>*`, and now every matching line is used. With samples/dcontrol.ctl, one unsigned message whose From: lists all 225 sender addresses caused 98 pgpverify runs, about 125 doit-line checks and 103 new groups in about 100 hierarchies, in 1.7-6 s. On main it was 0 runs, 1 group and 30 ms. It gives no new authority (only doit lines act), but it is a 50x amplification in the feed child. INN reduces Sender:/From: to one address first (cleanaddr). Fix: match one cleaned address, Sender before From and case-insensitive; one pgpverify per message also helps here.

Smaller:
3. **drop:** DeepSeek asked whether drop is the opposite of INN. It is not. INN's checkgroups.pl takes drop patterns out of the body, but docheckgroups only gets the exclusion patterns, so existing dropped groups are proposed for removal, the same as yours. One real difference: running INN 2.7's docheckgroups on your LaterLineWins setup removes `e2e.keep.old` (covered by a later line), while yours keeps it. Yours follows INN's documentation and is the safer choice. Maybe say "as INN documents" rather than "as INN does".
4. **An unknown action** (for example a typo `doti`, or only `break`) becomes a report line and takes its groups away from earlier lines (control.c ~1097-1116). INN rejects such a line ("is not a valid action"). Suggest: ignore it with a warning.
5. **When verification cannot run** (no PGP support, no pgpverifyargs, any dgpverify), the line is skipped and earlier lines act on its groups. INN with pgpverify off treats it as mail, which blocks earlier lines; main refused. None of the samples has an earlier line this could fall through to, but failing closed (the line blocks earlier lines) seems right.
6. **maxcheckgroups: changed meaning.** It now counts per group, not per first group of the message. A config written to main's sample (`comp.*:2000`) now blocks a Big-8 import, and the new sample limit covers only comp, news and rec, not all eight. changes/checkgroups-inn.md and the README row for TestCheckgroupsLimitLines are out of date.
7. **Logging and mail:**
   - "processing completed ok" is logged even when every line was skipped.
   - A line's own `=log` file is ignored.
   - Mail goes out only when a mail line acted, so a `drop,mail` line or a failed `verify-x,mail` line no longer mails.
   - A temp log created inside CgRun lacks the article dump.
8. **On an allocation failure,** CgReadRules or CgAppend drop rules or patterns, and earlier, broader lines then act. Suggest aborting the whole checkgroups instead.

Tests: on main, EveryLine, LaterLineWins, Drop and all three Maxdocheckgroups subtests fail with the stated assertions. VerifySkipped fails only through its 10 s timeout ("processing failed" versus the expected "completed ok"); a direct assertion would be faster. Gaps worth a test:
- a passing verify line taking groups from an earlier doit line (the ISC fixtures exist);
- the same key with different flags (item 1);
- a From: with several addresses (item 2);
- an unknown action;
- the legacy maxcheckgroups:;
