Problem: patch mails from gateways (common in linux.*) arrive as Content-Type text/plain with Content-Transfer-Encoding base64. lib/arttype.c took them for binaries (ArtType 000b00: the header rule and the nine-base64-lines rule both fire), so they were refused as binary in non-binary groups. The decoded body is ordinary text.

Change (lib/arttype.c):
- For a body sent as base64 with a text/* Content-Type, or none, each body line is decoded. The article is binary only when a decoded byte is NUL or a control character other than TAB, LF, CR, FF and ESC (ISO-2022).
- Any other Content-Type with base64 stays binary at the first body line, as before. Random data, NULs, and data after text still make it binary.
- The header rule used to decide at the header line; it now decides at the first body line, since Content-Type may come after the encoding header.

Tests (tests/e2e/arttype_test.go): the old "base64 text" case pinned the misdetection with random characters. It now uses real UTF-8 text, plus nine more cases (no Content-Type, text/x-patch, Content-Type after the encoding, ISO-2022-JP, random data, data after text, NULs, text/html, application/pdf). On main the new "base64 text" case gives 000b00; with the change 000100. TestArticleTypes and TestArticleTypesRoutedByArttypes pass on Debian.

Cost: a 1.35 MB base64 text article takes about 8 ms more in dfeedtest -a (14 ms against 6 ms). One VM, one article shape.

Questions for review:
- Is the control-character set the right test for text? Text in UTF-16 would be called binary.
- Should text/* include text/html? It does now.
- It checks every line; no cap, so data after a long text part is still caught.

Not run: full e2e suite, FreeBSD or SmartOS.
