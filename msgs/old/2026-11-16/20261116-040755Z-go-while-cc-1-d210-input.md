[Claude] D-210, our input (code read at upstream main 5a4f351; nothing run here; go-while has not decided anything, this is my analysis for both of you).

1. Which way: (a), a hash method without the CRC structure, used only for Message-IDs. Reasons:
- (b) stays linear. The fold maps two CRC words that differ by exactly 0x80000001 (top bit and bit 0) to the same value. A CRC is linear, so there is a fixed bit pattern (within about the last 8 bytes) whose flip gives exactly that difference. Same-length IDs that differ by that pattern still collide every time the top bit differs, just less visibly than one bit.
- With 62 random bits of MD5, the expected number of collisions in a history of 1.5e9 entries is about n^2/2^63, so about 0.24 over its whole life. Today it is about half of all pairs that differ in one bit position.
- (c) as the main fix costs too much: on a feeder with several peers, most offers are duplicates, and each would cost a spool read. Every by-ID lookup would also have to learn to walk past an entry for another ID. It is useful only as a check during the switch (point 2).

2. Rebuild: diloadfromspool already walks the spool and writes history entries (h.hv = hhash(id) at util/diloadfromspool.c:549 and :643), so with the new method it is the tool. For 1.5e9 articles the time is set by reading each article's headers: about 21 h at 20000 articles/s, about 3.5 days at 5000/s. Measure the rate on a slice of the spool first. The catch: entries for articles already expired from the spool but still inside the history's remember time are not on the spool, so a rebuild loses them, and old articles offered again would be accepted (reinjection). A way through: new entries with the new method; on a miss, look in the old history (old method, read-only). On an old hit whose article is still on the spool, read its Message-ID (the (c) check, only here); on an old hit whose article has expired, refuse as before. The collision risk is then left only for colliding pairs among expired articles, and only until the old history is dropped after the remember time.

3. Callers of hhash() besides the history:
- Group-name hashes, which locate the reader's overview files and must not change: util/dexpireover.c:659, :1409, :1472, :1496; util/doverctl.c:394, :447; util/dgrpctl.c:166 (via GFHash() or the "crc" H1.H2 names).
- Message-ID hashes outside the history, which have the same collision:
  - dreaderd/cache.c OpenCache()/CreateCache(): the cache file is named by the hash with no Message-ID check, so with readercache on, the second ID of a colliding pair can be served the first one's article from the cache. That is wrong data, worse than a lost article.
  - lib/precommit.c:141: hash only, so the colliding ID gets a short precommit deferral.
  - dreaderd/cancel.c:55/:66: the cancel cache.
  - util/diablo.c:3942: spamInfo.MsgIdHash.
  These are caches that can be thrown away, so moving them to the new method is cheap.
So I'd split it: hhash() stays as it is for group names and every on-disk name that depends on it; a new msgid hash (say hhash_msgid(), chosen by a new diablo.config method) is used by the history and its tools (lib/history.c, util/diablo.c, dilookup, dreadart, dhisctl, dcancel, dspoolrefeed, diloadfromspool, diconvhist, dhisbench) and by the Message-ID caches above.

4. compathash: agreed. On a miss it falls back to the old hash and finds the colliding entry again, so it brings the bug back for exactly these IDs. It is worth keeping only together with the (c) check from point 2, for the switch.

If Jesse picks (a), the cache issue in point 3 is a second D-entry worth filing now (the reader cache serving another article), whatever the history decision is.
