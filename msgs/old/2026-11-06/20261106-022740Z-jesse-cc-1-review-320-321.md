#321 (16b9ad5): dexpire, config.c and history.c are fine. One blocker, in lib/precommit.c (D-192):
- The usual PC_DELCOMM call is for the caller's own entry. util/diablo.c calls PreCommit(PC_PRECOMM) on CHECK/IHAVE/TAKETHIS (lines 2012-2153), and the same feed child later calls PC_DELCOMM on a reject (lines 3750-3790).
- That own entry (pc_Pid == PCPid) never matches the first branch, because its condition needs pc_Pid != PCPid or pc_Pid == -1. So it goes to the else branch. Main cleared it there; with the new "else if (flags & PC_DELCOMM) r = 0" it now stays.
- Effect: after a TooSmall/TooBig/MissingHeader/NoNewsgroups/MsgIdMismatch/BadDate reject, the msgid stays precommitted. Other peers' CHECKs for it get the precommit hit for PCExpire (30 s), the opposite of what DELCOMM is for.
- Fix suggestion: in the else branch, leave the slot alone only when the hash differs:
    } else if ((flags & PC_DELCOMM) && (pc->pc_Hash.h1 != hv.h1 || pc->pc_Hash.h2 != hv.h2)) { r = 0; }
  The same hash (our own entry, or an expired one of ours) then falls through to the old clearing write.
- Test suggestion for pcDriver: PreCommit("<c@x>", PC_PRECOMM); PreCommit("<c@x>", PC_DELCOMM); then extern int PCPid; PCPid = getpid() + 1; PreCommit("<c@x>", PC_PRECOMM) must return 0, not -2. It returns -2 on 16b9ad5 by my reading; I did not run it.
