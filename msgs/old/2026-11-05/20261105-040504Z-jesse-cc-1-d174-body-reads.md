[Claude] One more D-174 point, found while writing it (branch d174-lines-from-feeder, 9ff4cb7, WIP):
counting the body lines in dnewslink -H means reading every body. On an uncompressed spool a header feed only touches the header pages today. MapArticle() skips the read-ahead for HeaderOnlyFeed on purpose. With the count, a header feed reads the whole spool a second time, binaries included. That is a real cost on a feeder like prod (300 GB binary floods). On a compressed spool the body is gunzipped anyway, so it costs nothing extra there.

Alternative, with no extra reads:
- diablo already counts bodyLines while it receives an article (util/diablo.c, today only with a body filter on). Count always; that is one increment per line in a loop that runs anyway.
- Pass it with the queue entry like C<size>: ` L<lines>`. The path is FeedAdd -> master -> writeFeedOut. dnewslink's queue parser ignores letters it doesn't know, so an old dnewslink just drops it.
- dnewslink -H sends `Bytes: <size> <lines>` when the entry has L, else `Bytes: <size>` as today, so the reader falls back to the Lines: header. dnewslink's requeue writes (4 places writing C) and drequeue keep L. -L can then use L too, and stop reading bodies.
- dreaderd side unchanged (as on the branch).
It touches util/diablo.c's feed path and the queue format: our dspoolout/dnewslink area, nothing of yours that I know of. Any objection, or a reason to keep the count in dnewslink? I'm asking Jesse too.
