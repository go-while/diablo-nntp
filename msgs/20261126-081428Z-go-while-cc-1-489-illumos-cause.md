[Claude] #489 on illumos: reproduced on our OmniOS VM (kvm@arc1-ca/121-omnios, r151060d), and the cause is shown: a problem in the test's fault-injector shim, not in dreaderd. One agent ran it; I read its report; the runs are saved with headers. openai: n/a.
Cause: the injector shim finds a file's name by reading /proc/self/path/<fd> (tests/e2e/lock_results_test.go:488). On illumos tmpfs the first open by name after a rename(2) over an existing file has no readable path there (the readlink fails), so the shim gets "", does not match "dreader.access" and does not refuse the first fgets(); dreaderd reads the whole new file on that first pass, and only the retry 5 s later is refused: "1 time, 1 refusal" (or 0 and 0) instead of 2. CI uses /tmp (TMPDIR unset), which is tmpfs on illumos. Your CI log agrees: the first read logs "Invalid access definition : bogus in line 4 ... Errors in dreader.access file" (a whole-file parse) and "Unable to read" only 5 s later.
Shell probe on the VM: on tmpfs the first open after `mv` over an existing file has no path, the second open is fine; the same after rm + mv; an in-place write is always fine; on ZFS (/var/tmp) the path is always right, which is why it passes on a quiet VM with TMPDIR on disk.
Badline subtest, three separate processes each, TMPDIR on tmpfs: the PR as is: 3 of 3 FAIL with the CI signature ("1 times", "refused 1 times, want at least 2"); main (s.WriteFile in place): 3 of 3 PASS; the PR's rename then the test opens the new file once by name: 3 of 3 PASS; the rename then os.Chtimes on it: 3 of 3 PASS; os.Remove of the old file then rename: 3 of 3 FAIL. The two passing variants work because the test's own lookup restores the path before the daemon's first open: a tiny race remains, not stressed.
Possible fixes (not tried): best, make the shim not depend on the kernel path: on illumos fall back to the path given to fopen()/open(), as the lock shim's tracked-fopen code already does (no race, any file system); smallest, keep the rename and do one name lookup of the new file right after it (os.Chtimes or an open) with a comment on the tmpfs behaviour. No daemon change is needed. Your call which one.
Not checked: os.Stat alone as the lookup; the dotted-name and link variants in a clean run (that series was void: leftovers in /tmp caused out-of-memory on the 1 GiB VM); why tmpfs clears the path on rename (illumos source not read); a clean load reproduction; whether the half-written-file flake #489 wants to fix exists on illumos at all. Running all three subtests in one process fails from the second subtest on even with main's variant: a memory artefact of the 1 GiB VM, not the PR.
