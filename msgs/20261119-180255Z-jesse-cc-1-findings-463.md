[Claude] findings 463 4cc053d7 (score 6). The fix itself is right: on our Debian test VM both subtests failed on base 3 of 3 and passed on head 3 of 3, and the pipelining/NEWNEWS/ratelimit regression run passed. One Medium, measured, that should be fixed in this PR:

1. Medium: 100% CPU while the rest of the reply goes out at the rate limit, when `bytelimit` and `ratelimit` are both set.
   - NNTerminate() ends with MBFlush() and an unconditional `FD_SET(conn->co_Desc->d_Fd, &WFds)` (reader.c:791-792). Under ratelimit, MBFlush() starts a TIF_WRITE timer (mbuf.c:103) and writes nothing while d_Timer is set (mbuf.c:53, :169).
   - With the new `NNTerminate(conn); return;` (reader.c:1236-1237), co_Func stays NNTerminate. So select() returns at once for the writable socket, NNTerminate sets WFds again, and this repeats until the queued reply has gone out at the rate. ARTICLE output is not held to MBUF_HIWAT, so that is the whole article.
   - On base, the NNCommand2() after the terminate ended the throttling (co_ByteCountType = DRBC_NONE), and nothing set WFds again.
   - Measured with a temporary e2e test, not committed: readerdef `bytelimit 300` + `ratelimit 2000 article`, a 20 KB article from the spool, ARTICLE <id> and then read to EOF.
     - base: 0.0 s wall, 0.03 s dreaderd CPU;
     - head: 9.1 s wall, 9.04 s CPU;
     - head with the fix below: 9.7 s wall, 0.00 s CPU.
   - That is one fork's core per session that reaches its quota, for queued bytes / rate seconds. The PR text's "the busy-wait gets longer" understates it: on this path base had no spin at all.
   - Fix, tested on the VM: in NNTerminate(), `if (conn->co_Desc->d_Timer == NULL) FD_SET(conn->co_Desc->d_Fd, &WFds);`. ScanTimers() sets WFds when the timer fires, so the close still happens. With it, TestReaderByteLimitStopsPipelined, TestPipeliningReader*, TestDeepRevRatelimitRangeEqualBounds and both measurement tests passed. A test like the measurement (CPU time of the dreaderd fork, or a wall/CPU ratio) would guard it.

2. Low, test only, no change needed: the local (HELP) subtest's race on main comes from NNWriteHello() -> NNCommand() -> NNCommand2() reading HELP in the pass in which the fork takes the connection (HandleReaderMsg(), reader.c:580). The close check of that pass belongs to the THREAD_READER desc, so the client's next pass answers DATE first. If HELP arrives later, the same pass closes it and main passes. The spool subtest is deterministic (NNFinishSReq() sets co_FCounter = 1, server.c:979). Your README row calls the local one a guard, which is accurate.
