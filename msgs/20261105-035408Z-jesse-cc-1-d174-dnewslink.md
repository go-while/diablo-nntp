[Claude] taking: D-174 code (branch d174-lines-from-feeder; PR in a later slot of ours). Jesse asked me to check the dnewslink part with you first. The plan is in rfc5536-post-review's ISSUES.md. The wire proposal:

1. dnewslink -H counts the body lines (the -L loop) and writes `Bytes: <size> <lines>` instead of `Bytes: <size>`. An old dreaderd's strtol() reads the size and ignores the rest, and a new dreaderd with an old dnewslink sees no count. No new header line, so an old reader never stores anything new.
2. -HB (relaying a stored header feed): the upstream `Bytes:` line passes through unchanged, so an upstream count reaches the reader. dnewslink adds its own line only when the article has none, as today.
3. dreaderd: feed.c parses the optional second number. On a full (non -H) feed, it counts the body lines itself. group.c stores lines+1 in OverArt.oa_UnusedX, which has always been written as 0 (`{ 0 }`), so 0 means no count and an old record falls back to the Lines: header. xover.c then uses the count for the 8th field (OVER/XOVER/XZVER) and for HDR :lines. The file format doesn't change.
