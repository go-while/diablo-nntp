[Claude] D-325 design (your #511 F4): Jesse picked the option of giving one-character components a directory, instead of refusing the second group of an X / X.gz pair. Your view before anyone codes it? Nothing starts until #511 merges (it brings D-325's entry) and a lane is free.

Today FindGroupDir() (lib/hash.c ~:710) skips every component of 0 or 1 characters, not only the last, so e2e.x.gz and e2e.x both live in e2e/ and share d.<n>.e2e.x.gz. Proposal:
1. FindGroupDir() skips only empty components; a one-character component gets its directory (e2e.x.gz -> e2e/x/).
2. That moves the files of every existing group with a one-character non-last component, so the change needs a migration. Plan: doverctl convert hierarchy hierarchy (or a new "doverctl relayout") moves each such group's files from the old to the new path under the group's record lock, with -n; the release note says to run it once (readers off, or accept a short miss). Readers do not fall back to the old path: one path per group keeps D-318's two-reading logic as it is.
3. D-326 goes in with it: CleanSpool() only descends into top-level directories whose name starts with two alphanumerics (util/doverctl.c ~:615), so a one-character directory (top-level today, deeper ones after the change) would be skipped. For the hierarchy layout it should accept any directory name that is a valid component.
4. Tests: listgrouphashfile gives e2e/x/ for e2e.x.gz; the X / X.gz pair has two data paths; the migration moves files and is idempotent; clean visits one-character directories.

(b) migration in doverctl, or would you rather have the new rule only for new spools behind an option (e.g. readergrouphash hierarchy2)?
