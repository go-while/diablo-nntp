[Claude] TestDclientReplyLineBoundaries/quit-read-error (ours, #467) on FreeBSD: reproduced on our FreeBSD 15.1 VM (8 vCPU), cause shown: a race between the test and the FreeBSD kernel; nothing in dclient is wrong except that it has no read timeout. One agent ran it; I read its report; saved logs with headers; openai: n/a.
What happens: the test gives dclient a 15 s context (dclient_replyline_test.go:143); dclient hangs in read() for the full 15 s, so Go kills it ("signal: killed"). "output 32768 bytes" is not a cap: dclient's stdout is a pipe flushed in 16384-byte blocks; it had printed the whole QUIT reply except the last 2 bytes, which sit in its buffer until EOF or an error. The test server ends the connection with SetLinger(0) and Close, which should send a reset. On FreeBSD that reset is ignored the first time because it arrives before the client's delayed ACK (the counter "ignored RSTs in the windows" rose by exactly 1 per run, passing runs too). The client then sends a challenge ACK; normally the server's kernel answers with a second RST 3 microseconds later and dclient exits 2 as the test expects. When the machine is sending many closed-port RSTs, that second RST is dropped by the kernel's rate limiter (net.inet.icmp.icmplim = 200 per second; kernel log "Limiting tcp reset response"); the client socket stays ESTABLISHED with no peer and dclient waits (sbwait, ESTABLISHED in the probe; packet capture of the missing RST). The limiter as the dropper is shown by the capture and a dose-response, not by switching icmplim off.
Rates: CI (freebsd job, jrehmer/diablo-nntp): two failures with the identical message on 2026-11-26 (job 139746296512, run 45771822994, main 6dd54cb3; job 139746553950, run 45771868597 attempt 1, head 9c551fe0); attempt 2 of the same run passed; about 2 of 39 job runs that included the test failed (about 5%); the first 35 since 2026-11-22 had 0.
