- A reader client whose session reached the readerdef `bytelimit` was still answered for commands it had already sent: after "400 ... Session byte limit reached." NNCommand() went on into NNCommand2(), which made itself the connection's next step again, so the next command got its reply and a second 400 before the connection closed. NNCommand() now stops after the 400, and the connection closes once its output is written. In our runs the ARTICLE-from-the-spool case failed on main every time, the HELP case only in some runs (the cause is not established). While the rest of the reply goes out at a `ratelimit`, the connection no longer spins on the CPU: NNTerminate() sets the write wakeup only when no rate-limit timer is pending (with a `ratelimit` for all reply types main already spun; with a `ratelimit` for ARTICLE only, the first version of this change would have made it reachable). Not changed: the limit counts only bytes already written to the socket, so a slow reader can still be answered further commands while up to 256K is queued.
