- dreaderd: a failed rename or a write error (disk full) while installing the access cache files went unnoticed, and short files could replace the cache in use; a failed rename also left new files next to old ones, which the readers then loaded as one set. The old cache is now kept on a write error; a file in use that cannot be kept as a link stops the install before anything is renamed; when a rename fails the files already renamed are put back and no new cache is announced, and if that fails too the lock file (or, if it cannot be removed, its stamp) and the files are removed (each failure logged) so that no process loads a mixed set. The install is tried again 5 seconds later. A crash in the middle of the renames is not covered. Every install after the first keeps a hard link to each file in use, so the db directory must be on a file system with hard links (not FAT, nor an SMB or FUSE mount without them), and the ownership, permissions and attributes of the cache files must allow the link (for example Linux fs.protected_hardlinks refuses a link to a file of another user). Where link() is refused with EPERM or EOPNOTSUPP the install fails and the log names what to check.
