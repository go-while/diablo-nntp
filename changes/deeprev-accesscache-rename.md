- dreaderd: a failed rename or a write error (disk full) while installing the access cache files went unnoticed, and short files could replace the cache in use; a failed rename also left new files next to old ones, which the readers then loaded as one set. The old cache is now kept on a write error; a file in use that can be kept neither as a hard link nor as a copy stops the install before anything is renamed; when a rename fails the files already renamed are put back and no new cache is announced, and if that fails too the lock file (or, if it cannot be removed, its stamp) and the files are removed (each failure logged) so that no process loads a mixed set. The install is tried again 5 seconds later. A crash in the middle of the renames is not covered. Every install after the first keeps each file in use as <name>.old, a hard link where it can. Where link() is refused with EPERM, EOPNOTSUPP/ENOTSUP, EXDEV or EMLINK (a file system without hard links such as FAT or some SMB and FUSE mounts, Linux fs.protected_hardlinks for a cache file of another user) the file is copied to <name>.old instead and this is logged once per install. Only when the copy fails too (for example a cache file of another user that the news user cannot read) does the install fail, and the log names what to check.
