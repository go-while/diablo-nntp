- dreaderd: reply codes from its backends must be the whole three-digit code the command defines, followed by a space or the end of the line (no tab, nothing glued to it), and an unknown code is an error: greeting, MODE READER, MODE READONLY, AUTHINFO USER (381, or 281 for a login without a password, which ended the connection before) and PASS (281), IHAVE (335), the end of a post (235), WHEREIS, ARTICLE, HEAD. An auth backend (Perl, NetRemote, file, cdb, db, radius, PAM) logs a user in only with "100 ..." or "110 <readerdef>"; before, any answer that started with 1 did ("199 no", "1garbage", and a bare "1"). A Perl checkuser (or another backend) that returns just "1" must now return "100 Success" (or "110 <readerdef>"), or every login it accepts is refused with 481; the contrib scripts already do. NetRemote's one-digit "1" stays accepted. The NetRemote answer is read up to its newline, not from one read.
- dreaderd: a backend reply that is neither the expected code nor a one-line refusal the command has (a malformed status line, or a code with lines after it) closes that connection after the client gets its refusal (430 for an article, 441 for a post), so the left-over lines are not read as the next reply. A post is not sent again after such a reply to its article. A WHEREIS or MODE READONLY reply that is neither the expected code nor a one-line refusal closes the connection too (a one-line refusal still falls back to ARTICLE, or uses the server as before).
